# A recovery that delivers a working project

The developer request is: **Bring the compiled donor's dash into JUJUMP while preserving its timing, jumping, gravity and landing.** Start the preview with `npm run dev:transfer`, then choose **Recover for JUJUMP** in the investigation section. Opening the page or viewing a recording makes no model request.

## What happens

1. The existing extraction investigation gives the configured Meta model the compiled donor, tool interfaces and disclosed human-mapped field hints. It does not supply the saved recovered implementation. Meta chooses code, hypotheses, interventions and inputs through the existing persistent worker and isolated experiment SDK.
2. Public progress describes evidence actually present: orientation, function-body inspection, a controlled intervention, a later model action linked to its result, development, freezing and separate acceptance. Enumeration does not count as body inspection. Milestones do not establish that an interpretation is correct.
3. Meta selects its inspected code and actual evidence, submits a candidate, and can revise against real development failures within the existing attempt limit. Freezing binds its source/build, contract and timer mapping. Acceptance is a separate call; failures cannot unlock another repair or acceptance attempt.
4. The host loads only this investigation's frozen, accepted publication. It checks all published file hashes, candidate identity and source/build identity. An incomplete investigation cannot substitute the earlier successful recovery.
5. The host runs 11 adapter conformance scenarios against the **new component**, then seven real JUJUMP browser scenarios. After building the final ZIP, it system-unzips that exact archive into a new temporary directory, runs three Node checks and repeats all seven browser scenarios on its separate static server. External browser requests are blocked.
6. Only a checked final archive receives a durable integration artifact. The UI then enables its play and download links. Existing gallery transfers, remixes, children and exports remain separate.

The adapter, runtime hooks, coordinate conversion and collision policy remain human-authored. The component's source/build is unchanged between acceptance, recipient checks and export. A new component is not installed in a recipient merely because donor acceptance passed.

## Interfaces and persistence

The existing `POST /api/investigations` request remains `{questionId: "extraction", idempotencyKey}`. `GET /api/investigations/<id>` now includes `task` for extraction jobs. It records the request, milestones, exact candidate/session identity, measured model usage and costs, attempts, acceptance scope, elapsed machine time and integration identity. Refresh reconnects to that same job. No automatic paid retry is added.

Checked artifacts live below the existing lab journal's `integrations/` directory. Their receipt binds the project manifest, exact ZIP, component, candidate, session and standalone verification. Reading an artifact verifies its identities again. New routes are:

- `/recovery-projects/<artifact-id>/project.zip`
- `/recovery-projects/<artifact-id>/validation.json`
- `/recovery-projects/<artifact-id>/receipt.json`
- `/recovery-projects/<artifact-id>/case-study.json`
- `/recovery-projects/<artifact-id>/play`

The play route redirects to a different localhost origin running the exported GET-only static server with a clean environment. Generated browser code does not share the lab's origin or API admission. Two preview servers are retained at most; shutdown cleans up their processes and extracted temporary files. A preview can be recreated after a restart from its durable artifact. Interrupted investigations retain their existing evidence and spending records; neither interpreter stacks nor unfinished task execution are claimed to resume automatically.

## Measurements and boundaries

The task report measures the actual run's requests, tokens, estimated cost, reserved cost, development attempts and accepted traces/updates. Task duration includes automated recipient/export verification. Registration, field mapping, ABI design, evaluator construction, adapter and host work were supplied beforehand; their construction time remains unmeasured. The runner accepts no manual source edits during a run. Developer time saved, baseline productivity, adoption and independent user validation remain unmeasured.

This integration supports the existing default donor configuration at 60 Hz, source body width 8, canonical `cooldown`/`remaining` state fields and JUJUMP's declared 0.5 horizontal scale. A different accepted configuration or timer interface can fail compatibility. JUJUMP retains its vertical physics and platform policy. Finite donor and recipient checks do not prove full-game equivalence, arbitrary binary recovery or general engine compatibility.

The $0.50 investigation ceiling, $10 persistent lab ceiling, exact token preflight, durable reservations, unknown-billing blocks and no automatic retries remain unchanged. Component publication may precede the concluding model request; its provenance records the recovery costs at publication. The complete task/investigation report records total settled usage including that conclusion.

## Local validation

`tests/recovery-investigation.test.mjs` uses injected responses and actual worker execution to exercise body inspection, a controlled experiment, a subsequent result-linked decision, real development failure, revision, freezing and separate acceptance. Its implementation fixture is human-supplied; it is not a model discovery.

`tests/recovery-integration.test.mjs` exercises a different component identity, the actual recipient checks and independent final ZIP checks, publication, tampering and failed boundaries. `tests/recovery-task-web.test.mjs` checks refresh/reconnection, delayed publication, mobile layout and unavailable links after recipient failure. All these checks make zero paid requests.

`npm run verify:guided -- --software` reproduces the Roadster guided demo with forced SwiftShader. A saved local comparison is in `assets/integration/recordings/guided-demo-software.json`: the original sequence exceeded its 60-second guided deadline; the changed sequence completed in 33.9 seconds with eight active updates and six meters measured. Guide rendering is batched without skipping physics inputs or updates; an offscreen player receives visibility after initialization. These are single local observations, not a hosted CI result or a reliability benchmark. Frontend browser tests retain their assertions and run with two test files at a time to bound graphics contention.

Saved recordings, human-scripted local verification and fresh Meta activity have distinct labels. The original incomplete recordings remain available. The actual fresh recovery outcome is recorded separately; a failed attempt must not be described as a completed extraction or integration.

## Original fresh Meta outcome

After 174 local tests and all 27 frontend tests in bundled Chromium passed, one fresh Muse Spark 1.3 extraction ran through the unchanged persistent journal. Run `5e570dca-e9aa-4b69-9d65-74d69bcc6e5f` used 16 generation requests, 190,881 input tokens, 6,486 output tokens (3,152 reasoning tokens), an estimated **$0.26616675**, and **$0 unsettled**. It took 53.0 seconds through failure. The persistent lab total became $1.0762734 of $10; the existing remix budget is separate and unchanged. No automatic retry or second paid attempt was made.

Meta chose a checkpoint at frame 30, changed the supplied human-mapped `remaining` i16 at address 22441 from 0 to 8, and applied identical rightward inputs for 20 updates. Actual control displacement was 40 pixels; intervention displacement was 84 pixels. The first subsequent update differed: 2 versus 7.5 pixels and inactive versus active ownership. A later model turn recorded a finding citing that actual experiment. This demonstrates a model-chosen intervention and subsequent evidence-linked action, not independent memory-layout discovery.

The run **failed completion**: no actual function body was inspected and no candidate was submitted, frozen or accepted. No new recipient integration or ZIP was published. The first program merely declared an uninvoked `main` function and performed zero host operations. The second used nonexistent root SDK methods instead of `sdk.static` methods. Both consumed the existing two-program allowance. The model later used low-level experiment tools, but never completed the code/recovery milestones. Two trials without edits were identical-input reproducibility controls; the model's descriptions implying different branch inputs do not change their recorded inputs.

The unchanged recording is `assets/lab/recordings/recovery-handoff.json`, available as **Meta recovery attempt · incomplete** without inference. The existing accepted gallery component is separate. Subsequent measured trials are preserved in the [November 2 campaign](../assets/benchmark/recordings/README.md); none submitted a candidate. Those campaign outcomes and limits remain unchanged.

## Staged recovery and development feedback

Recovery now uses a direct tool set for each stage: investigation, evidence selection, development, freezing, acceptance and conclusion. Completed inspection and a controlled intervention move the model toward selecting evidence. Development retains targeted code/trace reads and experiment tools; a passed candidate exposes freezing, followed by a separate acceptance request. Exhausted development or failed acceptance ends the run. The general investigation and native-discovery protocol are unchanged.

Once at most seven model requests remain and the inspection/intervention prerequisites are present, selection is the only offered action. Those requests are reserved for selection, three development attempts, freezing, acceptance and conclusion. Each new recovery request records its stage and offered tools in the durable journal. This is a scheduling bound, not a guarantee that the model will produce a valid or correct candidate.

The host compacts context at evidence selection and candidate submission, keeping the latest source, inspected code and every actual development failure. Trace pages retain inputs, motion, timers and watches while omitting repeated rendering fingerprints. Earlier development attempts retain summaries in model context and their complete original results in the journal. Development failures also include the two preceding measured frames and the exact input sequence, allowing the model to distinguish update order and direction changes. Acceptance remains separate and exposes no repair trace to the model.

Citation validation accepts any qualifying selected controlled experiment, rather than requiring the first one in the journal. Feedback lists the actual selected code and experiment IDs; it does not invent evidence or scientific interpretations. Compilation rejects missing named exports before behavioral evaluation. Invalid modules still consume request/tool budgets and retain their exact submitted source and errors. The three behavioral-attempt limit and all cost, time, token, and acceptance limits are unchanged.

The UI shows each candidate's passed development checks and its first donor-versus-candidate mismatch. A failed recovery still exposes no new project download. Final-ZIP verification explicitly requests Node's TAP reporter, preventing a successful test run from being rejected when a newer Node version changes its default output format.

It was never frozen, accepted or exported. The complete outcome is `assets/lab/recordings/stage-guided-recovery.json`, viewable without inference. This is a development trial after implementation changes, not an additional attempt in the frozen benchmark campaign. Preceding-frame feedback and earlier evidence-selection routing were added after this trial.
